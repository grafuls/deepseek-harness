# Agent Note：协作工作区支持仓库后端

Status: implemented

[English](2026-08-29-collab-repo-backed-workspaces.md) | 中文

部分已被[collab 异步仓库置备](2026-09-01-collab-async-repo-provisioning.zh.md)取代：克隆现在以后台、自动移除置备记录的方式运行，`collab-clone-failed` 不再作为应答。

## Problem

创建协作工作区只能生成「仅命名」的工作区，其数据目录在 collab 数据根下被实体化为空。没有从既有仓库起步的办法：成员必须先创建一个空工作区，再手动把自己的代码放进去。被要求的流程正好相反：创建时输入一个 GitHub 仓库地址，让该仓库被克隆到本地目录，并把克隆结果当作工作区——同时在「协作工作区」设置页上有一个条目，用于设定这些克隆落盘的默认目录。

## Decision

`collab/workspace.create` 接受可选的 `repoUrl`（省略或传空字符串即为仅命名工作区）。非空地址会让 collab API 网关克隆该仓库并把克隆注册为该工作区的数据：

- 克隆经由 collab 本地的无 shell `git clone` 运行器（`gitCloneRunner`，spawn 时不给子进程 stdin 并设置 `GIT_TERMINAL_PROMPT=0`），超时为十分钟，因此没有任何 shell 插值到达进程边界，且用户无权访问的仓库会以 git 的 stderr 快速失败，而不是停在交互式凭据提示上等待。
- 克隆目标是 `<cloneRoot>/<repoName>-<workspaceId>`，其中 `<workspaceId>` 是生成的工作区 id，`<repoName>` 是净化成文件系统安全组件后的仓库名，方便管理员认出克隆源自哪个仓库。`<cloneRoot>` 在 `collab` 设置命名空间的 `cloneDir` 被设置时取其值，否则取 collab 数据根下的 `workspaces` 目录。
- 该命名空间由 collab API 通过 `installSettingsSection` 挂载，因此「协作工作区」设置页（ui-collab 的一个 `settings.section` 条目，即 `collab` 命名空间）写入它，而网关 `Config` 中的 `cloneDir` 只在用户覆盖之前为组合默认值播种。
- 克隆失败会删除不完整的目标目录并以 `collab-clone-failed` 应答；不创建任何工作区记录，因此失败的仓库初始化不会留下任何东西。
- `collab/workspace.open` 与 `collab/workspace.dir` 对仓库后端记录把工作目录解析为 `record.clonePath`，因此每个成员共享克隆出的工作树作为所挂载工作区的数据。克隆路径存储在记录上而非重新推导，所以之后修改 `cloneDir` 不会迁移或孤立既有工作区。
- 访问门会咨询工作区服务的 `workspaceHolding(path)` 关系（规范克隆路径包含该路径的第一条记录），它覆盖数据根之外的克隆；数据根 `workspaces` 前缀之下的路径仍由既有的前缀检查覆盖。
- 私有仓库只有在操作员配置了服务端 git 凭据时才会克隆（`gitToken`，`gitHost` 默认 `github.com`，`gitUsername` 默认 `x-access-token`）。该凭据只是插件配置——刻意绝不经由 GUI 读回的设置命名空间路由——克隆通过一个临时 `GIT_CONFIG_GLOBAL` 携带的、宿主作用域的 `Authorization` 头把它发送给被钉住的宿主，该配置只存活于本次克隆并在任何路径上都会被删除，因此 token 永远不会到达 argv、工作区记录、克隆自身配置或线上诊断。

## Alternatives considered

- **客户端自选目录。** 被其取代的「选择一个目录」模型——浏览器指定宿主机路径。被否决：collab 进程作为一个服务器服务于许多用户；成员选择的宿主机路径是一次未受认可的、跨用户不一致的文件系统授权。仓库地址由服务端执行且统一，因此成员资格门禁保持有意义。
- **空工作区再加一个之后「克隆进去」的动词。** 被否决：它留下一个未完成初始化的悬空工作区，并且需要第二个权威来决定谁有权写入克隆；把克隆放进创建流程让注册与实体化保持原子，记录永远不会指向缺失的目录。
- **从当前设置推导克隆路径。** 被否决：移动默认克隆目录会孤立每个仓库后端工作区；把 `clonePath` 存储在记录上能让访问划定与挂载在之后任何设置修改下都保持稳定。

## Consequences

- 从地址创建工作区现在是一步完成的流程，克隆失败会有明确、本地化的失败横幅；创建入口（空态与侧边栏区块共用）会弹出包含工作区名称与可选仓库地址输入框的创建模态框。创建请求进行中时模态框保持打开并显示「创建中…」，按结果恢复：成功才关闭，失败时保持打开并显示横幅——绝不会在克隆仍在进行时无声关闭。
- 新的设置页是可选的：ui-collab 只在设置面存在时注册它（可选地读取 `settingsScope`），因此省略设置面的单用户 `web` 配置保持不变。
- 仓库后端工作区与数据目录工作区现在在数据存放位置上有差别；删除仍然只移除注册记录，有意识地把克隆（或数据）目录留在磁盘上。
- 克隆契约及其访问门保持服务端所有；UI 中的地址只是便利入口，不是执行点。
- 私有仓库的克隆在操作员配置服务端凭据之前以 git 的 stderr 快速失败，配置后经 basic auth 克隆；公开仓库照旧无需认证即可克隆，而凭据不拥有的宿主永远不会收到它，因此成员指向恶意地址也无法窃取服务端 token。
- 呈现创建失败暴露出一个潜在的主题缺陷：暗色主题的错误别名把横幅文字（`state-error-primary`）与背景（`state-error-secondary`）都映射成 `red-400`，因此任何错误横幅读起来都是空的。暗色主题现在用深红 `red-900` 作为错误横幅背景，使 `red-400` 文字可读；模态框在缺少 store 错误时也渲染通用提示，而不是一个空盒。
- 邀请接收面无需刷新页面也保持新鲜：打开管理器面板即刷新工作区列表与发给当前用户的待处理邀请，并且在 collab 面挂载期间，控制器以三十秒为间隔重新读取两者（在变更或可用性探测进行中时跳过）——页面加载之后发出的邀请会自动出现。
