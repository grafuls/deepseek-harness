# @deepseek-ai/dsh-client-ui-collab

English | [中文](README.zh.md)

The collab workspaces manager for the Web GUI. This browser plugin lists the workspaces the signed-in user belongs to, creates new ones (optionally bootstrapped from a GitHub repository the collab API clones into a configured local directory), accepts the invitations addressed to the user, and — for the selected workspace — shows its members and invitations, sends invitations, changes member roles, removes members, and deletes it. The collab API realises each workspace as a real Host workspace mounted over its reserved data directory, so sessions born inside it are shared and scoped to that workspace's data. The sidebar section (it owns the sidebar's Workspaces seat) auto-mounts every member workspace when it renders (mounting is idempotent, so sessions other members created appear on their own), and a session opens directly from its row. The sign-in gate itself is [dsh-client-ui-auth](../ui-auth/README.md), which this package composes after: ui-collab only renders once a collab session cookie authorizes the browser.

The plugin registers two entries, both composed out through slot declarators rather than mounted unconditionally: the collab section on the sidebar's sole Workspaces seat (`sidebar.workspaces` — the local browsing region was removed from the sidebar, so this block is the seat's only occupant, not a second labeled group), and the `shell.overlay` manager panel that renders the list and detail. The section renders a full section header ("Workspaces") with a compact toolbar (expanding search, the same group-by/order-by view-options menu, and the add-workspace button that opens the creation dialog) above a scrolling list of member workspaces; a workspace row expands to the sessions mounted in that workspace, each of which opens on click — there is no separate per-row "Open" button. Apply order against the slot owners (ui-layout; the picker registration in ui-workspace no longer touches this seat) is unconstrained; each registration waits on its own declaration with `slots.inject`. Both entries share one store handle created inside `apply`, so opening the manager from a section row and driving it from the panel read the same state. A third contribution — the Collaborative Workspaces settings page — registers into `settings.section` only when the settings surface is present (declared by ui-settings-general), exposing the `collab` settings namespace that carries the default clone directory and the optional shallow-clone depth for new repository bootstraps.

## What it mounts

- Node half (`src/index.ts`): inert — the package is entirely browser-side.
- Browser half (`src/client/`): an `apply` that creates the workspaces store and a controller over the collab RPC channel, then registers the two slot entries and the optional settings section. The store hook reaches components as the `useCollabWorkspaces` inject hook; the actions (open, close, open manager onto a workspace, mount every workspace in the background, open a session, refresh, select, create, invite, revoke, accept, set role, remove, delete) are passed through the inject face. Every product string — surface copy, error banners, and validation notices — lives in the `collab.ui` dictionary on the standard locale seat, so it follows the GUI's Language setting.

## Repository-backed workspaces

The create affordance (the manager's dashed entry and the section toolbar's add-workspace button) pops up a modal dialog carrying the collab workspace creation detail: a workspace name field and an optional `GitHub repository URL` field. Supplying a URL asks the collab API to clone that repository into a local directory and opens the clone as the workspace's data, instead of creating a name-only (empty) workspace. The clone target is the value of the `cloneDir` preference in the `collab` settings namespace when set, otherwise the collab data root's `workspaces` directory; the target directory name is `<repo name>-<generated workspace id>`, so an administrator can tell which repository a clone roots at. The clone runs in the background on the server, so the create answers immediately and the dialog closes on success; while the clone has not settled, the workspace row carries a `Cloning…` badge, its sidebar section row shows the same badge and disables New Session, and opening the workspace is refused with a `still cloning` banner. A failed background clone silently removes the workspace, so no registry record outlives a failed repository bootstrap. Once the clone settles, both workspace rows and the sidebar folder show the clone's working-tree state — current branch, abbreviated commit, and an uncommitted-changes marker — read by the collab API at view-build time, so members see where the shared tree sits without opening a terminal. A session started inside the workspace runs on its own branch named `<workspace>-<session>` (the server switches the shared tree when the session is created), so the chip doubles as the "which line is this work on" readout for every session. The selected workspace's detail carries a repository block once its clone has settled: the current branch chip, a "Push branch" action that opens a confirmation row loading a server dry-run preview (what would move onto which base), and — on the member's explicit confirm — the push outcome with compare and open-a-pull-request links for an HTTPS origin. The push is server-side through the collab API's git credential and never force-forces, so a moved remote tip is refused instead of overwritten; the repository URL is a UI convenience — the enforced clone and push contracts and their access gates live in the collab API.

The repository block also offers a "Sync" action next to "Push branch": it asks the collab API to fetch the origin's current state into the shared clone without touching the checkout or any session's branch (remote-tracking refs only), acknowledges with a transient note, and refreshes the list — the cooperative pull counterpart to a member pushing their own line. Pushing itself works through the server credential for the matching origin host, so members share commits even in a private repository without holding a token themselves.

## The collab surface contract

The manager talks only through the shared `/api` connection RPC envelope (`collab/workspace.*`, `collab/auth.status`), the same channel the rest of the GUI uses, so it rides the session cookie and needs no localStorage. The availability probe folds every failure — no collab surface mounted, no session cookie, transport error — to `hidden`, and the section and panel render nothing then: a single-user `web` install and an unsigned browser see an empty sidebar Workspaces seat (the local browsing region that would previously have filled it is gone). Collab workspaces appear only in this section — the section is the sidebar's only workspace surface, so there is no local list to keep them out of. The workspace role comes from the wire (`workspace.role`); UI gating of admin actions is presentation only, and the collab API gateway's `requireWorkspaceAndRole` remains the enforcement point. The invitation accept surface stays live without a reload: opening the manager panel refreshes the workspace list and the signed-in user's pending invitations, and while the collab surface is mounted the controller re-reads both on a thirty-second interval (skipping while a mutation or the availability probe is in flight), so an invitation sent after page load appears on its own.

## Model Experience

None, as this is a presentation-only workspaces manager; the workspace scoping it reflects is enforced server-side by the collab API gateway, which owns any model-visible effect.

#### KV Cache effect

The package contributes nothing to model requests, so it cannot invalidate cache reuse.

## Known Limitations and Deferred Work

- **Hidden rather than explanatory when unauthorized** — while the browser holds no collab session (or no collab surface is mounted), the section and panel simply do not render; there is no banner explaining why. The ui-auth gate is what answers that question on a collab instance.
- **Collab workspaces appear only in the Workspaces section** — the sidebar browsing region is gone, so the section is the sidebar's only workspace surface and owns the collab row actions outright: the row options menu (rename, open the manager, or delete — rename and delete apply for every member and are admin-gated at the collab gateway) plus the workspace rename dialog and the per-session rename/fork/archive dialog. Manage collab membership through the panel.
- **Sessions exist only after a mount** — a collab workspace that has never been opened in the GUI genuinely holds no sessions, because the mounted Host workspace is what materializes them. The group auto-mounts every workspace when it renders, which covers already-mounted ones, and the empty note explains the rest.
- **One shared instance plane** — workspaces share the single browser session cookie; a workspace does not host its own login or its own set of sessions. Sessions within a mounted collab workspace still land in that workspace's shared data directory.
- **Deleting a workspace removes the record and the settled clone** — `delete` confirms in the panel, then the server unregisters the workspace and removes the clone directory backing a repository-backed workspace (the user copy of the repo — any branches they pushed remain on the remote). A name-only workspace's reserved data directory is left in place for the host process to manage, matching the server-side delete semantics.
